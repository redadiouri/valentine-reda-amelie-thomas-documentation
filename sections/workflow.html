Notre workflow de collaboration

Chez NovaWeb, les quatre membres de l’équipe utilisent GitHub Flow : une branche par tâche, des commits précis et une relecture avant chaque fusion.

La branche main contient la documentation validée et sert de référence commune. Chaque modification est préparée sur une branche dédiée.

  1. Créer une branche pour sa tâche

    Avant de commencer une nouvelle tâche, enregistrer son travail en cours, puis partir de main à jour. Pour rédiger le workflow :

    git switch main
git pull --ff-only origin main
git switch -c docs/workflow

    Cette création se fait une seule fois. Si la branche existe déjà, la rejoindre avec git switch docs/workflow.

    Choisir un nom court, en minuscules, sans espaces ni accents, avec des tirets entre les mots : docs/ pour la documentation, feat/ pour une fonctionnalité et fix/ pour une correction.

  2. Modifier et vérifier son fichier

    Réda modifie sections/workflow.html, enregistre le fichier et contrôle les changements avant de les ajouter au prochain commit.

    git status
git diff

    git status indique les fichiers modifiés ou nouveaux. git diff montre les modifications non préparées des fichiers déjà suivis ; un nouveau fichier doit aussi être relu dans l’éditeur.

  3. Enregistrer un ajout cohérent avec un commit

    Sélectionner uniquement le fichier concerné, vérifier le contenu préparé, puis créer un commit avec un message qui décrit la modification.

    git add sections/workflow.html
git diff --staged
git commit -m "docs: expliquer les etapes du workflow"

    Un commit enregistre les changements sélectionnés dans l’historique local. Chez NovaWeb, chaque ajout ou correction cohérente possède son propre commit.

  4. Envoyer sa branche sur GitHub

    Au premier envoi, associer la branche locale à sa branche distante. origin désigne le dépôt partagé sur GitHub.

    git push -u origin docs/workflow

    Pour les envois suivants depuis cette branche, après de nouveaux commits :

    git push

    Plusieurs commits peuvent être envoyés ensemble : ils restent distincts. Cet envoi ne fusionne pas les changements dans main.

  5. Ouvrir une pull request

    Sur GitHub, ouvrir une demande de fusion depuis la rubrique « Pull requests ». Choisir main comme destination (« base ») et docs/workflow comme source (« compare »).

    Vérifier les fichiers proposés, donner un titre précis et expliquer les changements. Pour sa section, Réda demande une relecture à Valentine.

    Si la branche contient d’anciens changements non intégrés à main, ils apparaissent aussi : vérifier tout le contenu proposé.

  6. Faire relire et corriger

    Valentine consulte les fichiers modifiés dans la pull request. Elle vérifie les explications, les commandes, la structure HTML et la lisibilité.

    Si elle demande une correction, Réda reste sur docs/workflow, modifie son fichier, puis enregistre et envoie la correction :

    git add sections/workflow.html
git commit -m "docs: clarifier la relecture du workflow"
git push

    La même pull request se met à jour. Valentine relit la correction et approuve les changements lorsqu’ils sont prêts.

  7. Fusionner les changements validés

    Après l’approbation de Valentine, vérifier que les éventuels contrôles ont réussi et qu’aucun conflit ne bloque la fusion.

    Si le dépôt autorise cette méthode, choisir « Create a merge commit » pour conserver les commits individuels, puis confirmer la fusion. Les options de squash ou de rebase ne conservent pas le même historique.

    La section validée rejoint alors main et devient disponible pour toute l’équipe.

  8. Mettre à jour main et nettoyer la branche

    Après la fusion, supprimer la branche distante terminée depuis la pull request. Une fois tout son travail enregistré et envoyé, Réda met à jour son dépôt local :

    git switch main
git pull --ff-only origin main
git branch -d docs/workflow
git fetch --prune

    -d refuse de supprimer une branche dont Git ne reconnaît pas la fusion. En cas de refus, vérifier l’historique avec l’équipe avant de continuer. --prune nettoie les références distantes périmées.

    Les changements et les commits intégrés restent dans l’historique de main. Une nouvelle tâche commence sur une nouvelle branche.

Exemple : Réda améliore une explication, Valentine la valide

Réda souhaite préciser que les noms de branches utilisent des tirets à la place des espaces. Voici le parcours de cette modification chez NovaWeb.

  1. Réda propose son ajout

    Sur docs/workflow, il ajoute la règle dans sections/workflow.html, puis vérifie, enregistre et publie sa modification.

    git diff
git add sections/workflow.html
git commit -m "docs: preciser le nommage des branches"
git push -u origin docs/workflow

    Il ouvre une pull request vers main, intitulée « Préciser le nommage des branches », et demande la relecture de Valentine.
